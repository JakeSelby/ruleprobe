## Reproduction

At `8da9a62`, add any bullet under `## Unreleased` in `CHANGELOG.md`, as `AGENTS.md` asks of a
user-visible change, and run the gate:

- `python3 scripts/release_preflight.py` exits 1 with `CHANGELOG.md still has Unreleased entries; fold
  them into the version section`.
- `tests/test_release.py`'s `test_repository_itself_is_consistent` fails for the same reason.
- CI's `test` job runs the preflight on every push and pull request ("Version and changelog agree"), so
  the pull request fails its required check.

Found while building #19, whose changelog entry is the first since 0.1.0.

## Root cause

`errors()` in `scripts/release_preflight.py` refuses Unreleased entries whatever the mode. That refusal
belongs to a release: `docs/releasing.md` has the release PR fold `## Unreleased` into the version
section before the tag. Between releases the section is meant to collect entries, and CI calls the
preflight with no `--tag`, so the release-time rule fires on every ordinary change.

## Acceptance criteria

1. **Given** a changelog whose `## Unreleased` holds entries and whose version section agrees with
   `__version__`, **when** the preflight runs without `--tag`, **then** it reports no error.
2. **Given** the same changelog, **when** the preflight runs with `--tag v<version>`, as the release
   workflow does on a tag, **then** it still refuses the Unreleased entries.
3. **Given** the release procedure in `docs/releasing.md`, **when** step 2 checks the release PR,
   **then** its preflight command passes `--tag v<version>`, so it still refuses stray Unreleased
   entries; **and** `main()` hands the flag, or a tag ref's `GITHUB_REF_NAME`, to that check. The
   release PR's CI run no longer refuses them on its own: see the review findings.

## Design

Apply the Unreleased check only when a tag is given. The version and dated-heading checks stay
unconditional, so CI still proves `__version__` and the changelog agree on every change. The release
workflow already passes `--tag "$GITHUB_REF_NAME"`, and `docs/releasing.md` step 2 now passes `--tag
v<version>` too, so the release PR keeps the full check: the tag string is only compared with
`__version__` and need not exist yet.

Rejected:

- Dropping the preflight from CI: CI would stop proving the version and changelog agree.
- A separate `--release` flag: `--tag` already marks a release, in the workflow and in step 3.

Must not change: the other checks, the release workflow, or the message a release sees.

## Regression test

`tests/test_release.py::test_unreleased_entries_pass_between_releases` fails against the 0.1.0
preflight (it returns the Unreleased error) and passes after. The old refusal test becomes
`test_unreleased_entries_are_refused_on_a_release`, run with a tag.

## Review findings

Code review, four layers (blind hunter, edge-case hunter, verification gap, acceptance auditor):

- **Patched, medium:** no test ran `main()`, now the only path that turns the refusal on, by `--tag`
  or by a tag ref's default. Added `test_main_passes_the_tag_to_the_unreleased_check`.
- **Patched, low:** the red-before and mutant claims now carry their command and output above, and the
  file list names `issue-map.json`.
- **Deferred, medium, maintainer's call:** a release PR that leaves entries under `## Unreleased` now
  passes CI; only the two documented `--tag` runs (steps 2 and 3) refuse it before the tag, and
  `release.yml` refuses it after the push, which would cost the version number. Enforcing it in CI,
  for example with `--tag` whenever a PR changes `__version__`, is new CI logic, so it is logged in
  `deferred-work.md` and raised with the maintainer rather than decided here.
- **Deferred, low, pre-existing:** the Unreleased check matches only `- ` bullets under a literal
  `## Unreleased`; `* ` or `+ ` bullets or a `[Unreleased]` heading would slip past. This repository
  writes neither.
- **Rejected, false:** "the record claims a refresh and a solutions note the diff lacks". The review
  diff was the fix commit alone; both land as a second commit in this pull request, as the maintainer
  asked of the first 0.2 PR.
