## Story

As a developer whose rules the catalog leaves unmeasured,
I want to see each unmeasured rule section with its nearest detectors and the reason it did not
bind, and record the binding I confirm,
so that my rules are measured after a few minutes of setup, by a claim I made and can see.

## Context and value

Epic 8 (#128, RP-E010) aimed for rules measured with no configuration. Story 8.6 (#151, RP-S025)
built a held-out set the binder had never been tuned on, `ruleprobe/corpus/rules-heldout.json`,
and catalog binding measured recall 0.12 (5/40) at precision 1.00 there (validated on that
synthetic set, not on real transcripts). On real, dense rule files per-sentence binding measures
almost nothing, and the approved plan's own exit clause cut the goal. On 2026-10-03 the
maintainer chose the replacement: an explicit, deterministic, opt-in `ruleprobe bind` that shows
each unmeasured section with its nearest catalog detectors and the reason it did not bind, and
records the binding the user confirms. There is still no model, and no false bind the user did
not choose. Catalog auto-binding stays exactly as strict as it is.

## Acceptance criteria

1. **Given** unmeasured rule sections, **when** `ruleprobe bind --plan` runs, **then** it prints
   them sorted by rule id, each with candidate detectors ranked by the binder's own evidence and
   the reason it did not auto-bind, `--json` prints the same plan as data, and nothing is written.
2. **Given** a plan with `bind:` set on some sections, **when** `bind --apply FILE` runs, **then**
   it writes `~/.config/ruleprobe/bindings.yaml` (honouring `XDG_CONFIG_HOME`), or with
   `--project` the repository's `.ruleprobe/bindings.yaml`, each entry naming the rule file
   (home-relative or project-relative), the section slug, the detector id and the sha256 of the
   section's normalized text, with sorted keys and entries and no timestamp.
3. **Given** a binding whose hash matches, **when** `report` runs, **then** the rule reads
   `measured  user-bound, <detector>`, apart from `catalog-bound`, and `coverage.user` counts it.
4. **Given** a section whose text changed after it was bound, **when** `report` runs, **then** it
   reads "binding stale, run ruleprobe bind" and is not counted as measured.
5. **Given** a `.ruleprobe/bindings.yaml` in a project found only through the transcripts,
   **when** `report` runs, **then** it is not read, and the coverage block counts it; the global
   file and the project of the working directory or `--rules` are honoured.
6. **Given** an unknown detector id, **when** `--apply` runs, **then** it is refused, nothing is
   written and the exit status is 2; a bindings file entry that tries to define a detector is
   refused at `report`.
7. **Given** any `report` run, **when** it finishes, **then** no file was written.
8. **Given** the same rules and choices, **when** `--plan` and `--apply` run again, in any order of
   choices, **then** they give the same bytes.

## Design

### Approach

- New module `ruleprobe/bindings.py` (AD-19): the bindings file format, `load_trusted`,
  `ignored_files`, `Bindings.apply`, the plan (`plan`, `_candidates`, `plan_text`) and the apply
  path (`choices`, `resolve`, `merged`, `write`). `rules.py` does not import it; `load_bundle`
  takes a `bindings` object and calls its `apply`, so the dependency runs one way.
- `rules.py` records each section rule's `(heading, paragraphs)` in `Bundle.sections`, threaded
  through `read_rule_file(sections=)`, `_section_rules` and `load_rules_dir(sections=)`; an id two
  sections share is recorded as None and never binds. `known_ids()` is the shipped, live catalog
  and loaded detector ids. `SOURCES` gains `user`; `Bundle.registry`, `_sourced` and
  `load_bundle` add a user-bound catalog detector to the registry exactly as a catalog-bound one.
  `coverage()` gains `user`, and `summary()` prints `user-bound` and the ignored-files count.
- `section_digest` hashes the heading and each paragraph through `rules._normalize`, one per line,
  so a markup-only edit keeps the binding and a word change makes it stale.
- `cli.py`: `bind (--plan [--json] | --apply FILE [--project])` with `report`'s `--root`,
  `--runtime`, `--since`, `--rules`, `--detectors` and `--no-config`. `_bundle_for_rules` is the
  bundle `report` builds; `_bundle_and_registry` reads the trusted bindings unless `--no-config`
  and counts bindings files at the discovered working directories.
- The plan is the declarative subset with a comment header, so `bind --plan > plan.yaml` is the
  file the user edits; `--apply` reads YAML or JSON. Each section carries `rule`, `sha256`,
  `reason`, `candidates` (`detector`, `evidence`), `bind: null`, and `stale` (the old detectors)
  when its binding went stale.

### Decisions and alternatives

1. **Apply re-reads the rules and checks each choice's hash against the section today.** The
   plan names the rule id and hash, never a path: the path written is derived from the rule file
   this run read, so a hand-edited plan cannot point a binding at an arbitrary file, and a section
   edited between plan and apply is refused. Rejected: writing the plan's own fields through.
2. **All or nothing.** Any refused choice (unknown id, changed section, catalog-measured section,
   a file outside the project for `--project`, an unreadable existing bindings file) writes
   nothing and exits 2, naming each. Rejected: writing the valid subset, which leaves the user
   unsure what was recorded.
3. **A user binding applies only where the catalog left a section rule unmeasured.** Catalog
   binding runs first and is unchanged; a dark or catalog-measured rule ignores its binding. A
   one-rule file with no section has no slug and is out of scope.
4. **Re-binding a section replaces every binding it had** in the file written; other sections
   are kept. `bind:` may be a list, which binds several detectors.
5. **The global file honours `XDG_CONFIG_HOME`,** as the global detector file does, and
   `--no-config` reads no bindings file, since bindings are the user's configuration.
6. **Project root.** `report` walks up from the working directory and from `--rules` to the
   nearest `.ruleprobe/bindings.*`, as `discover` does for detector files; `--project` writes at
   the nearest directory holding `.ruleprobe` or `.git`, else the working directory. Project paths
   compare by real path, so a working directory spelled through a link still matches.
7. **Ignored files are counted, never read or named,** like refused rule files (RP-S024).
8. **Candidates rank by sentences matched, then catalog order;** evidence names the unbinding
   words and the entries matched together. A section no pattern matched has no candidate, and
   none is guessed (RP-S024 decision 6); the plan header says any `ruleprobe detectors` id may be
   named.
9. **No interactive mode.** The plan and apply path is complete and is what the tests drive; a
   TTY prompt is left for later.
10. **Writes go through a temporary file and a rename** in the target folder, and a link or
    non-file at the target is refused.

### Do not implement

- Any change to catalog patterns, the binder's strictness or its corpus score.
- An interactive TTY flow.
- Binding a one-rule file with no section, or naming a plugin-only detector id.
- Reading a bindings file from a discovered project.

   raised a traceback. Fixed: `bind --plan` says so and points at `--json`, exit 2. Test:
   `test_a_rule_id_the_subset_cannot_spell_points_at_json`.
