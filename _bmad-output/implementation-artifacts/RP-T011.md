## Goal

Cut `0.3.0rc1` for the 0.3 beta (Jake, 2026-10-12: "take your recs", the recommendation being a
candidate now), installable as `uvx ruleprobe@0.3.0rc1` while `uvx ruleprobe` stays on 0.2.0. The
release tooling refused a pre-release by design (`test_prerelease_version_is_refused`), and the
tag workflow would have moved `stable` to one.

## Acceptance criteria

1. **Given** `__version__` `X.Y.ZrcN` with a dated section, **when** the preflight runs with the
   matching tag, **then** it passes; any other pre-release form is refused.
2. **Given** a candidate for a patch, **then** the preflight holds it to the series contract.
3. **Given** a final release, **then** its section never resolves to a candidate's.
4. **Given** a candidate's tag, **when** the release workflow runs, **then** the GitHub release is a
   pre-release and `advance-stable` does not run; `advance_stable.py` refuses the tag, `--check`
   included.
5. `docs/releasing.md` says how to cut a candidate and how the release folds after one.

## Dev notes

- The reference sites stay put: ruleprobe-site's `repin.yml` and jakeselby.com's
  `ruleprobe-card-check.mjs` both read `releases/latest`, which excludes pre-releases.
- A candidate's changelog section is a dated artifact and never rewritten; the release's section
  opens with a pointer to it.
- The workflow's `contains(github.ref_name, 'rc')` is safe because the preflight, which runs first
  in the same workflow, accepts no other tag containing `rc`.
- Files: `scripts/release_preflight.py`, `scripts/advance_stable.py`, `.github/workflows/release.yml`,
  `tests/test_release.py`, `docs/releasing.md`. No changelog entry: the package is unchanged.
