# RP-C004 — ci(release): a version bump that leaves Unreleased entries fails CI

## Goal

Make CI refuse a release PR that bumps `__version__` but leaves entries under `## Unreleased`. Since
#64 (PR #65) the preflight refuses Unreleased entries only with `--tag`, so every PR can carry its
changelog line. That left the release PR guarded only by the two documented `--tag` runs in
`docs/releasing.md`, and by `release.yml` after the tag is pushed, which costs the version number.
The maintainer chose on 2026-09-23 to close the gap in CI. It must land before the 0.2.0 release
PR (#58).

## Acceptance criteria

1. **Given** a PR that changes `__version__` in `ruleprobe/__init__.py` and leaves an entry under
   `## Unreleased`, **when** CI runs, **then** a required check fails with the preflight's Unreleased
   error.
2. **Given** a PR that leaves `__version__` alone and adds an Unreleased entry, **when** CI runs,
   **then** every required check passes, as #64 made it.
3. **Given** a release PR that folds the changelog as `docs/releasing.md` step 2 describes, **when**
   CI runs, **then** every required check passes.
4. **Given** a push to `main`, **when** CI runs, **then** it behaves as today; the new check applies
   to pull requests.

## Tasks

- [x] Decide where the "version changed" test lives: a step in the `test` job of
      `.github/workflows/ci.yml` that reads the base branch's `__version__`, or a preflight option that
      takes the base version (AC: 1 to 4)
- [x] When the version changed, run `python scripts/release_preflight.py --tag v<version>` (AC: 1, 3)
- [x] Tests for any preflight change in `tests/test_release.py`; for a workflow-only change, record
      the evidence of a failing and a passing run in the dev agent record (AC: 1 to 3)
- [x] Say in `docs/releasing.md` that CI now refuses an unfolded release PR (AC: 1)

## Design

- **Decision:** a preflight option, `--base-init PATH`, takes the base branch's
  `ruleprobe/__init__.py`. When its `__version__` differs from the package's, the run checks as a
  release, exactly as `--tag v<version>` would; an explicit `--tag` wins. The `test` job gets a new
  step, `A version bump is a folded release`, run only on `pull_request`: the job checks out with
  `fetch-depth: 2`, and the step writes `git show HEAD^1:ruleprobe/__init__.py` to `$RUNNER_TEMP` and
  passes it. `HEAD^1`, the merge commit's first parent, is the base the PR was built on; fetching the
  base branch's tip instead would make a re-run of an older PR's CI, after a release lands, compare
  the old version with the new one and fail an ordinary PR.
- **Why:** the comparison is unit-testable in `tests/test_release.py`, and the script still reads
  only files; `git` stays in the workflow, so the script's "only what a file can prove" promise holds.
- **Alternative rejected:** a workflow-only step that greps both versions in shell. It works, but
  its only evidence would be CI runs, and it duplicates the version regex outside the script.
- The existing `Version and changelog agree` step is unchanged (AC 2); pushes to `main` skip the new
  step (AC 4). A base whose `__init__.py` declares no `__version__` fails the step with a
  `ValueError`, which is loud rather than silently passing.

## Dev notes

- The `test` job checks out with `actions/checkout` at its default depth, so the base branch is not
  present: a workflow step needs `git fetch --depth=1 origin "$GITHUB_BASE_REF"` and then
  `git show FETCH_HEAD:ruleprobe/__init__.py`, or the base version passed in some other way.
- `release_preflight.py` promises to check "only what a file in this repository can prove"; reading
  the base branch's `__init__.py` keeps to that, but calling `git` from the script is new for it.
- Keep the existing "Version and changelog agree" step unchanged, so AC 2 holds.
- Repository tooling only: nothing under `ruleprobe/` changes, so no changelog entry.

## Review findings

One-shot route: `bmad-code-review` ran four layers (blind hunter, edge-case hunter, verification gap,
acceptance auditor); its blind hunter stood in for the one-shot route's own layer.

- **Patched, medium:** the step fetched the base branch's tip at run time, not the base the checked-out
  merge commit was built on, so re-running an older PR after a release would compare the wrong
  versions. It now reads `HEAD^1` of the merge commit, with `fetch-depth: 2`.
- **Patched, low:** `--tag` precedence and the folded-bump path were not really exercised; both tests
  now pin the derived tag, and the second checks the "checking as" line. The docstring is rewritten.
- **Patched, low:** the file list and the mutant's evidence are recorded above.
- **Proved in CI, medium:** the failing path had never run in real CI. The pull request carries a
  temporary commit that bumps `__version__` and adds a dated section while Unreleased entries stay,
  and a revert commit follows it. The run failed only at the new step: every other `test` step passed, and the step printed `checking as v0.2.0` and the Unreleased error ([run 35934953671](https://github.com/JakeSelby/ruleprobe/actions/runs/35934953671)). That run also shows `HEAD^1` reading the base on a real pull-request merge commit.
- **Deferred, low:** `AGENTS.md`'s gate block does not name the pull-request-only step. Its fix edits
  an agent-context file; logged in `deferred-work.md`.
- **Rejected, low:** "a retargeted base does not re-run the check"; adding the `edited` trigger would
  re-run CI on every title edit for a rare case.
