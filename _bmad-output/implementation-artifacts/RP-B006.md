# RP-B006 — fix(report): an order detector opening on events with no tool-use id keeps its compliance

## Reproduction

At `8eb957d`, compile an `order` detector whose `first` opens on an event with no tool use id, and
measure a session in which it opens twice in one turn:

- The detector: `{"id": "o/result-then-bash", "event": "session", "when": {"order": {"first":
  {"kind": "tool_result"}, "then": {"tool": "Bash"}}}}`.
- The session, all in turn 1: two `tool_result` events, then a `Bash` tool use.
- `measure()` gives `rules: {"o/result-then-bash": 2}`, `compliance: {}` and a `rules_errors`
  entry `{"error": "MalformedOpportunities", "hook": "opportunities"}`. The hits stand; the
  compliance is lost.

The same happens when `first` opens on two `assistant_text` or two `user_prompt` events in one
turn. No shipped detector opens on an id-less event today. Found by the Epic 2 retrospective,
finding F8 (`epic-2-retro-2026-09-24.md`).

## Root cause

`_a_order` in `ruleprobe/matchers.py` builds each opportunity point with `_hit(event)`, which
names a `tool_use_id` only for a `tool_use` event, so every other event it opens on gives
`(turn, None)`. `_tally` in `ruleprobe/report.py` refused any repeated `(turn, tool_use_id)`
point as malformed, a rule RP-S012's second review added for hand-written callables. AD-11 says
each event `first` matches opens one opportunity, so the producer's output was right and the
consumer's rule was too wide: `None` names no event, so two `(turn, None)` points are two events,
not one event counted twice. No test ran a compiled detector's output through `measure()`
(finding F9), so the conflict passed the suite.

## Acceptance criteria

1. **Given** an `order` with `first: {kind: tool_result}` and two tool results in turn 1 followed
   by a `Bash` call, **when** `measure()` runs, **then** the row's compliance is `{"opportunities":
   2, "followed": 2, "undecided": 0}` and it has no `rules_errors`.
2. **Given** a hand-written `opportunities` that repeats `(turn, None)`, **when** `measure()` runs,
   **then** each triple counts, decided or undecided.
3. **Given** a hand-written `opportunities` that repeats a `(turn, tool_use_id)` point with an id,
   **when** `measure()` runs, **then** it is still refused as `MalformedOpportunities`.
4. **Given** every compiled detector in the AD-11 identity test, the shipped catalog's included,
   **when** its result over each session passes through `measure()`, **then** `measure()` accepts
   it and its compliance equals the triples' own counts; a detector `measure()` refuses fails the
   test.

## Design

### Approach

`_tally` refuses a repeated point only when it carries a `tool_use_id`; a `(turn, None)` point is
never recorded in the seen set, so each such triple counts. `_tally` is the one place triples are
validated: `_compliance` calls it for `measure()`, and the report's `_is_tally` checks summed
tallies, not triples. The rule is explained once, in `_tally`'s docstring.

### Decisions and alternatives

- 2026-09-24: a repeated point with no tool use id is several opportunities, not a malformed
  result; a repeated point with an id stays refused, since an id names one event and two triples
  for it count that event twice. This narrows RP-S012's 2026-09-23 malformed-result decision.
- Rejected: giving id-less points an identity in `_a_order`, such as the event's index. It would
  change the triple shape AD-11 and the public `Detector` docstring fix, and a hand-written
  callable would still hit the same refusal.
- Rejected: dropping the repeated-point check altogether. The id-bearing case is a real detector
  error, and RP-S012's test for it stays.

### Must not change

The triple shape, `run()`, hit counts, the other malformed-result checks, and the
`MalformedOpportunities` name a row records.

## Regression test

- `tests/test_opportunity_points.py::test_an_order_opening_on_two_results_in_one_turn_keeps_its_compliance`
  is the retrospective's reproduction through `measure()`. Against `8eb957d`'s `report.py` it fails
  with `compliance: {}`; with the fix it passes. Its siblings cover `assistant_text` and
  `user_prompt` openings, an id-less hand-written repeat, and the id-bearing refusal.
- `tests/test_opportunities.py`'s identity test now adds the shipped catalog, an `order` opening on
  `tool_result` and a session with two results in one turn, and passes every result through
  `measure()`. Against `8eb957d`'s `report.py` it fails for `o/result-then-bash`.
