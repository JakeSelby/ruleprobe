## Story

As a maintainer of a rule set,
I want each detector entry to carry the schema it was written under,
so that a newer entry is refused loudly instead of loading wrong.

## Context and value

FR-27 puts a schema version on every declarative detector entry. In 0.1.0 no entry carries one:
`ENTRY_KEYS` in `ruleprobe/matchers.py` is `id`, `rule`, `event`, `when`, `gate`, `kind`,
`description` and `examples`, and the top-level `version: 1` in `ruleprobe/detectors/common.yaml` is
ignored. Without a version, an entry written for a later schema loads under the old reading and
counts wrong with no signal. This is part of the one 0.2 break (AD-9) and depends on the value
RP-D001 (#29) fixes.

## Acceptance criteria

1. **Given** an entry with no `schema_version` and a file with no top-level `version`, **when** it
   loads, **then** it is read as schema 1.
2. **Given** a file whose top-level `version` is a known schema, **when** an entry omits the key,
   **then** the entry takes the file's value; **and** an entry's own key wins over the file's.
3. **Given** a top-level `version` or an entry `schema_version` that is not a known schema version
   (above the highest known, `0`, a negative number, a string, a float or a boolean), **when**
   discovery loads it, **then** it is a finding with file, line and reason, the entry (or, for a
   top-level `version`, every entry that takes it as default) does not load, and the rest of the file
   still loads. Each of those value shapes has its own test case. [ASSUMPTION: an entry with its own
   known `schema_version` still loads under a bad top-level `version`, since its own key wins]
4. **Given** `ruleprobe/detectors/common.yaml` (top-level `version: 1`), **when**
   `tests/test_equivalence.py` runs, **then** it still matches `common.py` hit for hit.

## Design

### Approach

Per AD-9: the key is `schema_version`, absent means 1, the file's top-level `version` is the default
for its entries, and an entry's own key wins. Add `schema_version` to `ENTRY_KEYS` and validate it in
`compile_detector`; read the file-level default in `ruleprobe/rules.py` (`_entries`,
`_compile_entries`) and pass it down. A value that is not a known schema version is a finding through
the existing finding path, carrying file, line and reason, and only the affected entries are dropped.
The highest known version is the RP-D001 value.

### Decisions and alternatives

- Type and value: fixed by RP-D001 (#29), not here.
- A boolean is rejected as a version even though Python treats it as an integer, as the existing
  `_count` and `order within` checks in `ruleprobe/matchers.py` already reject booleans.

### Do not implement

- No `schema_version` on rows or `report_data` (RP-S008).
- No new matcher or widened declarative subset beyond the one key (AD-7).
- No migration of an entry from one schema to another.

### Completion notes

- `compile_detector` validates an entry's own `schema_version`; `rules.load_file` reads a
  `detectors:` file's top-level `version` as the default. An unknown file value is one finding on
  its line, and only mapping entries without their own key are skipped; a top-level
  `schema_version` in a detectors file is the same kind of finding, since the file-level key is
  `version`. Rule-file front matter has no file-level default.
- The constants `SCHEMA_VERSION = 2` and `KNOWN_SCHEMA_VERSIONS = (1, 2)` live in
  `ruleprobe/registry.py`, the one module both `matchers` and `report` may import under AD-1, so
  entry validation here and row versioning in RP-S008 share one definition (RP-D001's value).
- Deviation from the Design: the effective version is neither passed to `compile_detector` nor
  carried on the `Detector`, although the Design says "pass it down". 0.2 reads schema 1 and 2
  entries the same way, so the file default only decides which entries are skipped.
- A file-level finding (a bad `version`, or a top-level `schema_version`) states how many entries
  it skipped and lists their ids; when both are present, both are reported.
- `ruleprobe/detectors/common.yaml` is unchanged at `version: 1`; raising it to 2 is left to the
  maintainer.
- Tests are in a new `tests/test_schema_version.py` rather than `test_matchers.py`,
  `test_rules.py` and `test_declarative.py`, so parallel stories editing those files do not
  conflict. `test_equivalence.py` still passes unchanged (AC 4).
