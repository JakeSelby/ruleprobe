- F5 (edge case; reproduced). Two runtime flags over one root read different Gemini files.
  - With `--runtime gemini --root <dir>`, `_paths` returns early through `gemini.transcripts`,
    which reads files under a `chats` directory only (`readers/__init__.py` lines 229 and 230).
  - With `auto --root <dir>`, every `.jsonl` file whose first line `gemini.recognises` is read as
    Gemini, wherever it sits (lines 231 to 235).

  The file skipped under `--runtime gemini` is not added to `errors`. The shipped corpus shows it:
  `gemini-writes.jsonl` sits outside any `chats` directory (RP-S019's build-time decision 1).
  Over `ruleprobe/corpus/sessions`, `auto` reads four Gemini sessions and `--runtime gemini` reads
  three, with no error either way. `measure` gives `gemini-writes.jsonl` three
  `secrets/secret-in-write` hits, so those hits are counted under `auto` and never under
  `--runtime gemini`. The only
  test is for the `gemini` path (`tests/test_reader_gemini.py` lines 443 to 447). *Instance:* fix
  now: one rule for both paths, or an `errors` entry for the set-aside file, with a test for each
  path. *Prevention:* none.
- F6 (adversarial; reproduced). A write the user edited is counted against the agent. A synthetic
  session held one `write_file` whose args carried an access-key-shaped string with
  `modified_by_user: true`, while `ai_proposed_content` held a placeholder.
  `secrets/secret-in-write` hit it. The key was the user's text, not the agent's, so the hit is an
  over-count, which the package contract says to avoid. The README says Gemini's gaps "under-count
  on it rather than guess" (line 379). This case is not listed there, and it does not
  under-count. No test covers it: searching `tests/` for `modified_by_user`, `ai_proposed` and
  `cancel` finds nothing. *Instance:* fix now. Read `ai_proposed_content` when
  `modified_by_user` is true, or keep such a write native. *Prevention:* F3.
- F7 (adversarial; reproduced). A cancelled call becomes an ordinary `tool_use`. In the same
  probe, a `write_file` with `status: "cancelled"` and the same key gave the second
  `secret-in-write` hit. Whether a call the user refused should count may be a matter of policy:
  the agent did attempt it. This run did not check whether the other two readers count a refused
  call, so the parity question is open. *Instance:* the maintainer decides, and records the answer
  in RP-S019 with a test. *Prevention:* F3.
- F8 (adversarial; observed). `report --runtime gemini --root ruleprobe/corpus/sessions` prints
