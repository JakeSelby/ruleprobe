# RP-B005 — fix(detectors): no-verify counts a hooksPath override only when it disables hooks

## Reproduction

1. A synthetic Bash tool use: `git -c core.hooksPath=.githooks commit -m x`.
2. Run the shipped `verification/no-verify` over it, through `ruleprobe.run` or the corpus.
3. Observed on `46f3528`: one hit. The detector counted any token starting `core.hooksPath=`
   as a bypass, so a repository that turns its own tracked hooks on through `-c` scored as
   skipping them. In the field sample (#53), 5 of 6 distinct no-verify hits had this shape.

## Root cause

`no_verify` in `ruleprobe/detectors/common.py` matched `t.startswith("core.hooksPath=")`
over every token of the git segment, and its declarative twin in `common.yaml` and the
catalog restatement in `catalog.py` used `token_prefix: "core.hooksPath="`. Neither read the
value: `core.hooksPath` names the directory git runs hooks from, and only a path that holds
no hooks skips them. The prefix also matched a token after the subcommand, and missed a key
spelled in another case, which git accepts because config keys are case-insensitive.

## Acceptance criteria

1. **Given** `git -c core.hooksPath=.githooks commit -m x`, **when** `verification/no-verify`
   runs, **then** it gives no hit; the same holds for any other non-empty path but `/dev/null`.
2. **Given** `-c core.hooksPath=` (empty), `-c core.hooksPath=/dev/null`, their quoted forms
   and `-c core.hookspath=…` in any case, on a `commit` or `push`, **when** it runs, **then**
   it gives one hit.
3. **Given** the `--no-verify` or `-n` flag, or a `SKIP` or `PRE_COMMIT_ALLOW_NO_CONFIG`
   assignment, **when** it runs, **then** it fires as before, a tracked hooks path beside it
   included.
4. **Given** every case in AC 1 to 3, **when** the Python detector, its `common.yaml` twin and
   the catalog entry run, **then** they give the same hits (AD-7).
5. **Given** the corpus with a near-miss label for AC 1, **when**
   `ruleprobe corpus --no-config --floor 0.9` runs, **then** it passes with no false positive.

## Design

- The rule: a `-c core.hooksPath` override counts only when its effective value is empty or
  exactly `/dev/null`. A missing or any other path is not counted.
- `ruleprobe.shell.git_config(segment)` gives the effective `-c` settings before the
  subcommand: the last value per key, keys compared case-insensitively, as git keeps them.
  It steps over git's global options with their values (`-C`, `-c`, `--git-dir`,
  `--work-tree`, `--namespace`, `--super-prefix`, `--config-env`, `--attr-source`) through
  the same walk `git_calls` uses, and gives `[]` for a segment that is not a `git` call.
- The pattern `^(?i:core\.hookspath)=(?:/dev/null)?$` matches the key in any case and the
  value exactly, so `/DEV/NULL` does not count. It lives once per surface: `_HOOKS_OFF` in
  `common.py`, and the same string in `common.yaml` and `catalog.py`.
- The declarative format had no way to say this: `token_prefix` is a case-sensitive prefix
  over the whole segment, and `arg_regex` reads only arguments after the subcommand. The fix
  adds one additive `git` key, `config_regex`, searched in each effective setting from
  `git_config`, so the twin and the catalog stay hit-for-hit with the Python detector. A call
  where no setting matches and one is unreadable (a variable or substitution) is undecided,
  as `message_regex` is. Whether to keep the key is Jake's call, pending.
- Rejected: a `text` regex over the whole command beside a `git` block, which loses the
  segment scope and would fire on an `echo` of the override next to a plain commit, an
  over-count AD-4 forbids; and a `command.first_operand` regex, which sees only the first `-c`
  and cannot tie the override to a `commit` or `push`.
- Accepted under-counts, each named in the docstrings: a hooks path that is missing or empty
  on disk, which only the file system can tell; a setting given by `--config-env`; and one
  given by `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`.
- Changed beside the detector: `git_calls` now also steps over the values of `--git-dir`,
  `--work-tree` and the other valued global options, so every `git` matcher and git-reading
  detector sees `git --git-dir .git commit` as a commit.
- Unchanged: the flag and assignment spellings, `token_prefix` itself, and the detector id,
  rule and event.

## Regression test

`tests/test_no_verify_hookspath.py`: ten spellings that turn hooks off give one hit, and
thirteen that do not give none, `git -c core.hooksPath=.githooks commit -m 'feat(x): y'`
first; each case runs through the shipped detector, the `common.yaml` twin and the catalog
entry, which must agree (AC 4). The `.githooks` case fails on `46f3528` and passes after.
Further tests cover last-value-wins, the exact value, the global options, a non-git segment,
the flag and both assignments beside a tracked hooks path, `config_regex` with `args_any`,
an unreadable value, and a bad pattern. The corpus gains `4:tu-w7` in
`verification-hooks.jsonl`, a near-miss that was a false positive before. The catalog entry
gains a `/dev/null` positive and a `.githooks` negative in its `examples`.

## Review findings

`bmad-code-review`, round 1 (blind hunter, edge-case hunter, verification gap, acceptance
auditor), over `f050cc9`. Every patch was verified on the full gate afterwards.

- **Patched, should-fix:** an earlier `-c core.hooksPath=/dev/null` counted even when a later
  `-c core.hooksPath=.githooks` overrode it. `git_config` now gives the last value per key,
  keys compared case-insensitively, and both the detector and `config_regex` read that.
- **Patched:** `(?i)` also matched the value, so `/DEV/NULL` counted. Only the key is
  case-insensitive now.
- **Patched:** `git --git-dir .git -c core.hooksPath=/dev/null commit` was missed, because the
  walk stopped at `.git`. The valued global options are stepped over in one shared walk.
- **Patched:** `config_regex` gave a decided no-match over an unreadable value; it is undecided
  now, as `message_regex` is.
- **Patched:** the under-counts (`--config-env`, the `GIT_CONFIG_*` environment, a missing path)
  are named in the docstrings and in Design.
- **Patched, tests:** a bad `config_regex`, `config_regex` with `args_any`, `-n` and
  `PRE_COMMIT_ALLOW_NO_CONFIG` beside a tracked hooks path, `/dev/null` on `push`, the catalog
  entry over every case (AC 4), and `config_regex` in the catalog's key-coverage check.
- **Patched, record:** the Regression test counts, the rule stated exactly, and the corpus
  session's closing narration, which still described the session without its near-misses.
- **Held for the maintainer:** whether `config_regex` stays as a new key; kept for now.
- **Left to the orchestrator:** the `CHANGELOG.md` entry.
