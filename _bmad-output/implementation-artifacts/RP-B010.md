# RP-B010 — fix(detectors): whole-file-cat skips a cat inside a redirected group

## Reproduction

From #111, at `c9cc68d`: `transcript-hygiene/whole-file-cat` over a Bash call whose `cat` sits in
a group with a redirect after its close.

- Input: `{ cat header.txt; echo; } > out.txt`, and the subshell form
  `( cat header.txt; echo ) > out.txt`.
- Observed: one hit each. The `cat` writes `out.txt` and puts nothing in the transcript.
- The same holds for a nested group (`{ { cat a; }; echo; } > out.txt`) and a group piped into
  `head`, which is the `cat a | head` near-miss the detector already skips.
- Field evidence: both wrong hits in the field-precision spike's two samples (#53) had this shape
  (historical, as #111 reports it).

## Root cause

`_pipelines` in `ruleprobe/shell.py` dropped `{` and `}` as words with no meaning and read `(` and
`)` as plain separators, so a group's close and the redirect after it ended up in a segment of
their own (`[">", "out.txt"]`) and the `cat` inside was a sole segment with no redirect.
`whole_file_cat` in `ruleprobe/detectors/common.py` and the `command` matcher's `sole_segment`
and `redirect` keys read that segment as a lone, unredirected `cat`. Bash applies a redirect
after a group to every command in it, so the parse lost the one fact the detector needs.

## Acceptance criteria

1. **Given** `{ cat header.txt; echo; } > out.txt`, **when** the shipped detectors run, **then**
   `whole-file-cat` does not hit.
2. **Given** `( cat header.txt; echo ) > out.txt`, **when** they run, **then** it does not hit.
3. **Given** a nested group redirected only by the group around it, **when** they run, **then**
   it does not hit.
4. **Given** a group piped into another command, **when** they run, **then** it does not hit, as
   `cat a | head` does not.
5. **Given** a `cat` outside a redirected group (`{ echo x; } > out.txt; cat notes.txt`), or in a
   group nothing follows (`{ cat notes.txt; }`), **when** they run, **then** it hits.
6. **Given** a group the parse cannot follow, never closed or followed by a word, **when** a
   `command` matcher reads `redirect` or `sole_segment` on a segment in it, **then** the result is
   undecided, and neither the detector nor `not` of it hits (AD-4).
7. **Given** the shipped corpus with the new near-misses and positives, **when**
   `ruleprobe corpus --floor 0.9` runs, **then** `whole-file-cat` scores 1.00 and
   `tests/test_equivalence.py` passes.

## Design

The fix is in the shared parse (AD-5), not in a detector. `_pipelines` keeps a stack of open
groups: a `{` where a command would start and an unquoted `(`, closed by a `}` where a command
would start or an unquoted `)`. At each close it reads the words up to the next separator:

- a redirect operator tags the group `redirect`, with its target and an fd number before it read
  as part of it;
- a pipe tags it `pipe`;
- any other word tags it `unknown`, and so does a group the command never closes;
- nothing, or a separator, tags it nothing.

A group takes on the tags of the group around it, and each segment records its innermost group's
tags as `Segment.groups`, a sorted tuple. `Segment` is a `list` subclass, so a segment still
compares equal to its plain token list and no consumer of `pipelines` changes.

Readers of the tags:

- `has_redirect` is true for a segment in a redirected group, the way bash applies the redirect.
- `group_output(segment)` returns the tags, `()` for a plain list.
- The `command` matcher reads `sole_segment` as false for a segment in a piped group, and both
  `redirect` and `sole_segment` as undecided in an `unknown` group when nothing else decides
  them. Every other key keeps its answer.
- `whole_file_cat` and `unfiltered_find` skip a segment with any tag, which is the Python form of
  the same rule, so `tests/test_equivalence.py` holds.

Alternatives rejected:

- A regex for `} >` over the command text: AD-5 forbids a second decomposition, and a regex for
  command positions has backtracked before (docs/solutions, 2026-09-23).
- Appending a group's redirect tokens to every segment in it: it would change the arguments
  `git_calls` and `first_operand` see, and say nothing about a pipe.
- Deciding a stray close: a `)` with no open is a `case` arm, and closes nothing.

Must not change: hits on any command with no group, the token lists of every segment, and the
public names in the README. `unfiltered-find` changes in the same direction, since it reads the
same keys: that is the shared parse doing its job, and it is named in the changelog.

## Regression test

- `tests/test_detectors.py`: `whole-file-cat` cases for each acceptance criterion's shape, and a
  redirected-group case for `unfiltered-find`. Before the fix the four group near-misses and
  the never-closed group hit.
- `tests/test_shell.py`, `GroupTests`: the tags for a brace group, a subshell, nesting, a pipe, a
  `cat` outside the group, three unknown shapes, a quoted brace, a `case` arm, and a hostile-input
  timing test over deep nesting and closes followed by words.
- `tests/test_matchers.py`: `redirect` and `sole_segment` undecided, under `not` too, in a group
  never closed, and decided once a group closes.
- Corpus: turn 5 of `ruleprobe/corpus/sessions/hygiene-cat.jsonl`, five near-misses and two
  positives. With the parse change reverted the corpus reports 5 false positives for
  `whole-file-cat` (precision 0.71, below floor); with it, 1.00.

`tests/test_detectors.py`, `CHANGELOG.md`, `README.md` (the quoted corpus table), this file.

Known misses, in the `ruleprobe/shell.py` docstring: a `)` written against the next operator
(`(cat a)>out`) is one token, so that subshell never closes and is `unknown`; a redirect made
elsewhere, such as an earlier `exec >file`, is not read. `>|` and `&>>` are not redirect operators
to the parse, so a group followed by one is `unknown`. Each is an under-count.

Testing: `python3 -m unittest discover -s tests`, the 3.9 floor through
`uv run --no-project --python 3.9 python -m unittest discover -s tests`, and
`python3 -m ruleprobe corpus --no-config --floor 0.9`.
