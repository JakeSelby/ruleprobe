# RP-D012 — decision(readers): whether a cancelled or errored tool call counts as a tool use

## Context

Epic 5's retrospective (#26, finding F7) found that a Gemini CLI call whose `status` is
`cancelled` or `error` was emitted as an ordinary `tool_use`, so detectors counted it: a cancelled
`write_file` gave a `secrets/secret-in-write` hit. The Claude Code and Codex readers had not been
checked; both emitted every `tool_use` whatever its result said (historical, 0.2.0).

Two failure directions pull against each other. Counting a call that never ran over-counts: the
cancelled write wrote no key. Dropping every call that reported an error would make a test run
that exits non-zero vanish, so `testing/test-after-change` would report a change as untested when
it was tested. AD-4 (under-count rather than over-count) breaks a tie.

The question: for each reader, is a refused, cancelled or errored call an observation of the
agent's behaviour, and how does each transcript tell a call that never ran from one that ran and
failed?

## Options

1. **Count every call, as 0.2.0 does.** For: the agent did attempt it, and nothing in the
   reader has to know a runtime's refusal shapes. Against: a refused write of a key is a
   `secret-in-write` hit for a key that was never written, a false hit, which AD-4 forbids.
2. **Drop every call whose result reports an error.** For: one rule, easy to state. Against: a
   Claude Code `Bash` that exits non-zero is an error result, so a failing test run disappears and
   `test-after-change` reports a false "not followed".
3. **Count a call exactly when it ran.** Drop a call that never ran (refused, cancelled, denied by
   a permission rule or policy, stopped by a check before the tool ran); keep a call that ran and
   failed. Where a transcript cannot tell the two apart, take the under-count reading. For: each
   detector counts what happened, in both directions. Against: each reader must know its runtime's
   refusal shapes, and a refusal worded some other way is missed.
4. **Add an `executed` field to `tool_use` and let each detector choose.** For: no information is
   lost. Against: a schema change under AD-2 that every detector, built-in and user-written, must
   learn to read, to decide a question that has one answer for every detector.

## Decision

Option 3, taken 2026-10-03 under the maintainer's delegation and flagged to him for confirm or
override. A tool call is an observation of the agent's behaviour exactly when it executed. A call
that never executed makes no `tool_use` and no `tool_result`, so no detector counts it, for a
violation or for compliance. A call that executed and reported failure still counts. It beats
option 2 because a failed test run is still a test run, and option 4 because no detector needs the
other reading. Option 1 is the over-count AD-4 rules out.

How each reader tells the cases apart (implemented; tested on synthetic transcripts only):

- **Gemini CLI.** Each recorded call carries `status`: `success`, `error` or `cancelled`
  (`ToolCallRecord` and `CoreToolCallStatus` in Gemini CLI's source). A shell command that exits
  non-zero is `success`, with `Exit Code: N` in its output; `error` comes only from a tool error
  such as a failed spawn. `error` also covers refusals before the tool runs (invalid parameters,
  an unregistered tool, a policy denial), and `cancelled` covers a declined confirmation, a
  cancelled queue and a run the user stopped part-way. The record carries no error type, so the
  reader cannot separate them: only `success` counts, the under-count reading.
- **Claude Code.** A refused call's result is an error. Since 2.1 its line carries
  `toolDenialKind` (`user-rejected`, `cancelled`, `permission-rule`, `interrupted`); before it,
  the text is a fixed refusal: the user rejecting or cancelling the call, `Permission to use ...`,
  a `PreToolUse:<tool> hook error: ...` block, an interrupt marker, or a `<tool_use_error>` from a
  check before the tool ran (input validation, a cancelled sibling call). The line's markers are
  read only on a line holding one result; on a line of several, each result is decided by its
  own text. An error the running tool raised is `<tool_use_error>Error calling
  tool ...` and counts; a `Bash` that exits non-zero is `Exit code N` and counts. A result that is
  not marked `is_error` always counts.
- **Codex.** A refused call's output is fixed: `exec command rejected by user`, `patch rejected by
  user`, `patch rejected: ...` from the approval settings, `apply_patch verification failed: ...`
  for a patch that did not match the files and was never applied, or `aborted` for a call an
  interrupt cut off. Each is matched whole or by its prefix, never as a substring. Any other output is a call that ran, a command that exited non-zero included.

An interrupted call (Claude Code `interrupted`, Codex `aborted`, Gemini `cancelled`) may have
started, and none of the three transcripts says whether it did, so it is left out on every reader.

## Consequences

- Easier: a refused or cancelled write is no `secret-in-write` hit on any runtime, and a refused
  change opens no `test-after-change` opportunity. The three readers now agree on what a
  `tool_use` is, which `ruleprobe/events.py` states.
- Harder: each reader carries its runtime's refusal shapes, and a new refusal wording is missed
  until a reader learns it. Known misses (stated in the README): a Codex refusal worded otherwise,
  such as an exec policy's own reason, still counts; an interrupted test run no longer counts as
  following a change, so on that shape `test-after-change` can report "not followed" for a run
  that started. Like a runner the detector does not recognise, it can only lower the followed
  share, which the README already says to read as a floor, so the floor reading still holds.
- Counts change for users with refused or cancelled calls in their transcripts, so the change
  carries a CHANGELOG line under Unreleased. No detector, matcher or public name changes.
- The corpus gains never-ran calls in four sessions (a rejected and a denied Claude Code write, a
  rejected and an aborted Codex `find`, a cancelled and an errored Gemini write) with no label, so a
  reader that emits them again fails `ruleprobe corpus` on false positives. The Gemini suite run in
  `gemini-shell.jsonl` now exits non-zero and is still labelled as following its change.
- Field accuracy is unknown: the shapes come from each runtime's source or shipped build, not from
  real transcripts. Validating them on real sessions is open.
- AD-2 carries the rule as a dated amendment, made through `bmad-architecture` in this change.

## Review findings

Review of PR #156 at af5352f, 2026-10-03. No finding was a bug against the decision; each was a
gap in a reader's coverage of it.

1. **Codex counted an `apply_patch` that failed its own verification.** Codex answers it with
   `apply_patch verification failed: {error}` (`codex-rs/core/src/tools/handlers/apply_patch.rs`)
   and applies nothing, so `test-after-change` opened an opportunity for a change that never
   happened. Resolved: the output is dropped by that prefix, anchored. Tested.
2. **Claude Code did not recognise a PreToolUse hook's block without `toolDenialKind`.** The
   2.1.283 build words a blocking error as `${hook} hook error: ${blockingError}` with the hook
   named `PreToolUse:${tool}` (validated against its shipped strings). Resolved: an `is_error`
   result starting `PreToolUse:<tool> hook error: ` is dropped; `PostToolUse:` runs after the tool
   and still counts. Tested. Unverified: whether a build before `toolDenialKind` wrote this text as
   the result's content unwrapped, rather than inside `<tool_use_error>` (which is dropped either
   way). A hook's own deny decision carries free text and is recognised only by `toolDenialKind`;
   the README states that miss.
3. **`toolDenialKind` and `toolUseResult` were read per line.** In the 2.1.283 build every result
   line found is built with one result block, but nothing in the format forbids several, and older
   builds were not checked (unknown). Resolved: the line's markers are read only on a line holding
   one result; on a line of several, each result is decided by its own text, so a refusal cannot
   drop a sibling that ran. Tested with a refused write and a failing test run on one line.
4. **Test gaps.** Added: output that only contains a refusal word (`...Output:\naborted`) still
   counts, which fails if the Codex match became a substring match (checked by mutation); and one
   case each for `[Tool call not completed`, `[Tool call did not complete` and `[Tool call
   interrupted`.
