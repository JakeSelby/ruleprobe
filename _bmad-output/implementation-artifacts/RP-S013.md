## Story

As a developer with rules,
I want the report to show opportunities and followed beside hits per session,
so that I can say how often a rule was followed when it applied.

## Context and value

This is the user-facing half of maintainer decision 3. RP-S012 puts `compliance` in rows; this story reads it in `report_data` and `report`, applies the FR-22 minimum, settles the `promote?` wording (RP-D006) and folds renamed ids the same way hits fold. Today `report_data(rows, by, min_sessions, promote_share, registry, validity)` returns hits, sessions and share per detector with a `promote?` or `unobserved` note gated on `min_sessions`, and `report` prints the same numbers.

## Acceptance criteria

1. **Given** a fixture session with N opportunities of which M are followed, **when** `report_data` runs, **then** it gives `opportunities: N`, `followed: M` and `undecided`, and the table prints the same numbers beside hits per session, not in place of them.
2. **Given** a detector with no opportunity, **when** reported, **then** it prints hits per session only and no compliance figure.
3. **Given** fewer opportunities than the minimum (`min_opportunities`, a parameter of `report` and `report_data`, default from RP-D004), **when** reported, **then** counts print and no rate does; in `report_data` the rate field `compliance_rate` (`followed / opportunities`) is `null` and the table prints the same absence (FR-19). [ASSUMPTION: the field name `compliance_rate`, and `null` rather than an absent key]
4. **Given** `--by repo` or `--by stance`, **when** reported, **then** compliance is grouped the same way as hits.
5. **Given** the RP-D006 decision, **when** the table prints, **then** the threshold marker uses the decided wording and carries no advice.
6. **Given** the same rows, **when** reported twice, **then** `--json` is byte-identical.
7. **Given** rows whose `compliance` map is keyed by a retired detector id and rows keyed by its current id, **when** `report_data` runs, **then** `compliance` folds through the same fold function story 1.6 uses for `rules`, and `opportunities`, `followed` and `undecided` sum under the current id (AD-9, AD-11).

## Design

### Approach

Extend `report_data` to sum each row's `compliance` per group, after folding its keys through the one fold function (today `folded_rules`, generalised by 1.6). Add `min_opportunities` beside `min_sessions` to `report_data`, `report` and a CLI flag, and emit `compliance_rate` only at or above it. `report` prints the three counts and the rate in added columns beside the existing ones. Every map is sorted explicitly (NFR-3) so `--json` is stable. The `promote?` note changes only as RP-D006 decides.

### Decisions and alternatives

- The minimum's default and scope: RP-D004 (working default 20, per printed group, assumed).
- The marker wording: RP-D006.
- Compliance by position is out of 0.2.0 (RP-D007).
- 2026-09-23: `promote_share`, `--promote-share` and `RULE_PROMOTE_SHARE` are renamed to
  `frequent_share`, `--frequent-share` and `RULE_FREQUENT_SHARE`, as is the `report_data` key,
  following RP-D006 in the 0.2 break (the one release allowed to break the declared API). The
  spelling is a default the maintainer confirms or overrides. `RULE_FREQUENT_SHARE` is a module
  constant, exported from the package root as its predecessor was. (Decision R.)

Decisions taken in the build, 2026-09-23:

- **Decision A (AC2).** "No opportunity" means the detector defines no `opportunities` (None): no
  row carries compliance for it, so it gets no compliance keys and no columns. A detector with the
  hook and zero opportunities prints `0`, `0`, `0` and no rate (`compliance_rate: null`, `-`).
- **Decision B (failures never silent, deferred here from RP-S012).** A session whose
  `opportunities` raised or was malformed, or whose `fn` raised, is out of that detector's
  compliance figures; `opportunity_errors` counts those sessions per detector and a note names
  them. Hit figures are untouched.
- **Decision C (stored tallies).** A stored tally that is not three non-negative integers with
  `followed <= opportunities` is never read as zero: that session leaves the detector's
  compliance, and `malformed_compliance` counts it per detector with a note. A `compliance` that
  is not a map, or holds a non-string key, names no detector: the row is counted in the row-level
  integer `unreadable_compliance` with a note, and any readable entries in it still sum. A null
  `compliance` is read as absent. The "its hits stand" sentence prints once for all three.
- **Decision D (argument check).** `min_opportunities` must be an `int` and not a `bool`;
  anything else raises `TypeError`.
- **Decision E (ids).** An id carried only by compliance, an opportunity failure or a malformed
  tally gets a by-rule line and is seeded, at zero if need be, into its group's compliance. Such
  an id has no hit record, so its note is left blank, never `unobserved`.
- **Decision F (one population).** Under `--by stance` the rescan filter runs first, and
  `errors`, `opportunity_errors`, `malformed_compliance` and `unreadable_compliance` all count
  only the sessions that land in a group; the "no sessions with a known stance" return follows
  those counts.
- **Decision G (layout).** The share header is as wide as its cell, and the validity column starts
  past the widest note, so every note and validity cell starts under its header. The plain table
  header moves one column as a result.
- **Decision H (rate display).** The table prints `100%` only when every opportunity was followed
  and `0%` only when none was; any other rate is clamped to 1-99%. `compliance_rate` in the data
  is exact.
- **Decision I (export).** `RULE_MIN_OPPORTUNITIES` is exported from the package root beside
  `RULE_MIN_SESSIONS`.

### Do not implement

- No compliance by position in the session.
- No change to how hits, sessions or share are computed.
- No rate replacing hits per session.

### Completion notes

- `report_data` sums each measured row's `compliance` through `folded_compliance`, which reads
  through the same fold helper, `_folded_items`, as `folded_rules` (AC7). A tally that is not three
  non-negative integers with `followed <= opportunities` is skipped, never read as zero.
- By rule, a detector some row carries compliance for (or whose `opportunities` failed) gets
  `opportunities`, `followed`, `undecided` and `compliance_rate`; any other detector gets none of
  the four keys (AC1, AC2). By repo and by stance, each group carries `compliance`, detector id to
  the same four figures, sorted by id, possibly empty (AC4).
- `min_opportunities` (default `RULE_MIN_OPPORTUNITIES = 20`, per printed line or group, per
  RP-D004) is a trailing keyword on `report_data` and `report` and the CLI flag
  `--min-opportunities`; below it, and at zero opportunities, `compliance_rate` is `None` and the
  table prints `-` (AC3). Undecided points do not count toward the minimum.
- The table adds `opportunities`, `followed`, `undecided` and `rate` columns only when some detector
  has compliance. A report without any has the old columns, with the share header one character
  wider so it sits over its cell (Decision G); grouped tables add one indented line per detector
  with compliance.
- The marker is `frequent` (RP-D006, AC5), and the threshold follows it as `frequent_share`,
  `--frequent-share` and `RULE_FREQUENT_SHARE`; the declared call shape and its contract test
  moved with it. `RULE_MIN_OPPORTUNITIES` is exported from the package root.
- Stored tallies, unreadable maps, the argument check, compliance-only ids, one error population
  under `--by stance`, the layout and the rate display follow Decisions C to I.
- Deferred from RP-S012: a session with an `opportunities`-hook error for a detector, or with a hit
  error for it, is out of that detector's compliance figures; `opportunity_errors` counts the
  failing sessions per detector and a note names them, so a failure is never silent.
- Verified with the repository gate script over the worktree; every exit code 0.

### Round 1: build review (2026-09-23)

1. The `promote_share` / `--promote-share` rename was not done. Resolved: renamed to
   `frequent_share` / `--frequent-share` with the declared call shape and contract test (Decision R).
2. A stored tally failing validation was dropped silently. Resolved: counted in
   `malformed_compliance` with a note; a negative-count case added (Decision C).
3. Groups omitted a detector whose `opportunities` failed in every session; ids with only
   compliance had no by-rule line; failures were counted before the rescan filter. Resolved:
   seeded, given lines, counted after the filter (Decisions E, F).
4. `min_opportunities` unchecked, a no-op `.strip()`, a 117-character line, and no root export.
   Resolved: `TypeError` (Decision D), removed, wrapped, exported (Decision I).

   "of sessions".
