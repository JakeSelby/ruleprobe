# RP-D013 — decision(catalog): whether test-after-change keeps compliance as its hits

## Context

`testing/test-after-change`, from the catalog (#49, RP-S016), is the one catalog row that counts
compliance. Each file change opens an opportunity, and a hit is a change that a later test run
followed. Every other row counts violations, where fewer hits is better. The README and the
detector's description say so.

AD-4 says a missed hit is a quieter report and a false hit is a wrong one. On a violation row, a
detector gap makes the figure quieter. On this row a gap runs the other way, because a test runner
the detector does not recognise leaves its change counted as not followed. The description lists
those runners: one behind `env` or `sudo`, a wrapper not listed, a build tool given another target
first (`mvn clean test`), and one whose other option takes a value before the target.

The field-precision spike (#53) judged 50 sampled hits: 44 right, none wrong and 6 unsure. That is
precision, and it says nothing of the runners the detector misses.

The question: should the row be re-expressed as violations, so that every row reads the same way?

## Options

1. **Keep compliance as the hit**, as shipped in 0.2.0.
   - *For:* a runner the detector misses becomes a missed hit, which AD-4 prefers, and `explain`
     never shows a hit that did not happen.
   - *Against:* the row reads the opposite way to the others, and its followed share errs low.
2. **Re-express it as violations**, so that a hit is a change no later test run followed.
   - *For:* every row reads "fewer is better".
   - *Against:* each runner the detector misses becomes a false hit, the over-count AD-4 forbids,
     and `explain` would present it as evidence. It would also break the catalog's shipped meaning
     and its corpus labels.
3. **Keep it, but open an opportunity only in a session where some test run was recognised.**
   - *For:* fewer changes are wrongly counted as not followed.
   - *Against:* it blinds the row to the case the rule is about, a session that never runs its
     tests.

## Decision

Option 1, decided on 2026-09-24 under the maintainer's delegation. It is the only shape in which a
detector gap produces missed hits rather than false ones, which is AD-4's direction for hits. The
cost is that this row's followed share is a floor, and the README now says so.

## Consequences

- No code, detector or corpus change: the catalog, its labels and the 0.2 contract stand.
- The README's catalog passage says that a test run the detector does not recognise leaves its
  change counted as not followed, so the followed share is a floor.
- Recognising more runners, such as `mvn clean test`, raises the floor without changing the
  direction. Each addition carries a corpus near-miss, as every detector change does.
