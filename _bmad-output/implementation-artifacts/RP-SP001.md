# RP-SP001 — spike(report): time the sixty-second path on a reference volume

## Question

Does `ruleprobe report --rules --since 30` finish within sixty seconds over the reference volume of
500 sessions and 200 MB of transcripts? NFR-9 states this bound, but no timing has been measured and
the bound is derived from SM-1, not from a benchmark. The answer decides whether NFR-9 holds as
written or needs a follow-up for performance before SM-1's cohort runs.

## Experiment

- Build a synthetic reference volume: 500 sessions, about 200 MB, in a native runtime's transcript
  format, with no real transcript content (AD-6). A generator script under `scripts/` if needed.
  [ASSUMPTION: from epics.md Story 3.6]
- Run on a build with the catalog (RP-S016) and section-level binding (RP-S015) in place, over a
  sectioned rule file.
- Time `ruleprobe report --rules <dir> --since 30 --root <volume>` wall-clock, cold and warm.
  [ASSUMPTION: several runs and the worst taken; the corpus names one timing]
- Record the exact command and the machine class.

## Exit criterion

Within 60 s wall-clock on the reference volume: "within 60 s". Over 60 s: "not". A "not" files a
follow-up issue rather than fixing inside the spike.

## Result

**Within 60 s.** The worst of every series finished in under 1.1 s on the reference volume, and in
under 3 s on a denser variant of the same size, more than twenty times inside the bound.

- **Build:** `9ca5651`, which carries the catalog (RP-S016), section-level binding (RP-S015), the
  subagent-session reader (#86) and the Gemini reader.
- **Machine:** Apple M5 Pro (`sysctl -n machdep.cpu.brand_string`), 15 cores, 24 GiB
  (`hw.memsize` 25769803776), macOS 26.5, internal SSD. Python 3.14.5; the floor run on 3.9.25.
- **Volume:** `python3 scripts/reference_volume.py <volume> --anchor 2026-09-24` (seed 50): 500
  transcripts, 75 of them subagent files, 206.2 MB, 74,131 lines. `--since 30` kept 429 sessions
  holding 60,490 events.
- **Command:** from the repository root,
  `python3 -m ruleprobe report --rules tests/fixtures/catalog/team --since 30 --root <volume>`, and
  the same with `--json`. The rule file binds seven catalog entries by section; the report
  measured all seven.
- **Timing:** wall-clock by `/usr/bin/time -p`, each run a new process, exit 0 every time. A cold
  run had an empty bytecode cache (`PYTHONPYCACHEPREFIX` set to a new directory); the first came
  straight after generating. Dropping the file cache needs root, which the run did not have, so
  "cold" is a cold interpreter over a volume the OS had just written.

| Series | Runs (s) | Worst (s) |
| --- | --- | --- |
| Text, cold | 1.07, 0.96, 0.95 | 1.07 |
| Text, warm | 0.95, 0.86, 0.85 | 0.95 |
| `--json`, cold | 0.95, 1.02, 0.96 | 1.02 |
| `--json`, warm | 0.88, 0.86, 0.90 | 0.90 |
| Python 3.9.25, text, cold | 1.48, 1.09, 1.11 | 1.48 |
| Dense variant, text, cold | 2.87, 2.68, 2.62 | 2.87 |
| Dense variant, text, warm | 2.52, 2.57, 2.52 | 2.57 |
| Dense variant, `--json`, warm | 2.52, 2.56, 2.54 | 2.56 |

The cold text run's first figure is by `perf_counter` around the command, 1.07 s, as its
`/usr/bin/time` file was not yet written; every other figure is `/usr/bin/time`'s `real`. The text
and `--json` outputs were byte-identical across runs, and the 3.9 text output matched 3.14's.

- **Sensitivity:** most of the volume's bytes sit in a few long tool outputs, which parse cheaply.
  The dense variant held the same 500 transcripts and 212 MB with short outputs only, 276,628
  lines, about 3.7 times the reference volume's line count; the time grew with lines, not bytes, and
  stayed under 3 s. It was generated by the same script with its tool output patched to short
  outputs in the timing session, not a shipped option.
- **Still to re-run:** #87, the copied-session dedupe still in progress, may add a pre-scan over
  every transcript before the report reads it. The orchestrator re-runs the command above on the
  same volume after #87 merges and records the figure here.

## Decision

**Within 60 s: NFR-9 holds as written.** No follow-up for the slow path is filed. Whether to publish
the machine the timing came from is a publishing question for the maintainer (NFR-9).
