## Story

As a developer with a `CLAUDE.md` of twelve rules,
I want twelve entries in the coverage block,
so that each rule is measured, dark or unmeasured on its own.

## Context and value

Today every `.md` under `--rules` is one rule (`load_rules_dir` and `read_rule_file` in
`ruleprobe/rules.py`); a file without front matter is one unmeasured rule. A stranger's unedited
`CLAUDE.md` is therefore one entry, whatever it says. FR-15 splits it into one rule per unit so the
catalog (RP-S016) has something to bind and the measured share (RP-S014) means something. The unit is
fixed by RP-D008; this story assumes headings. [ASSUMPTION: RP-D008 chooses headings, per its working
assumption]

## Acceptance criteria

1. **Given** a fixture file with three rule sections and one section holding only a fenced example,
   **when** read, **then** it yields three rules and the coverage block counts three.
2. **Given** a unit that is only a heading, a fenced block, a table or a blockquote, **when** read,
   **then** it is not a rule and is in no state.
3. **Given** a section rule, **when** its id is formed, **then** it is `<path>#<heading-slug>`, and it
   is unchanged after a section above it is edited.
4. **Given** two sections with the same slug, **when** read, **then** the second takes `-2` in document
   order; a collision that remains is a finding.
5. **Given** a file bound in front matter (FR-13), **when** read, **then** it keeps one rule with its
   0.1.0 id and state.

## Design

### Approach

In `read_rule_file`, keep today's path for a file whose front matter carries `detector:` or `opt_out:`
(AC 5). Otherwise split the body into units per RP-D008, drop units with no line of text outside a
fenced block, a table and a blockquote, and return one `RuleEntry` per remaining unit, each
`unmeasured` until RP-S016 binds it. `load_rules_dir` extends its rule list with every entry. Ids
follow AD-12: path relative to `--rules`, `#`, heading slug, ordinal suffix for a repeat, and a
remaining collision appended to findings.

### Decisions and alternatives

- The split unit: RP-D008. If it chooses list items, AD-12's id form is amended there and ACs 3 and 4
  are revised before build.
- Id from heading text, not position, so it survives an edit above it (FR-15, AD-12).

### Decisions taken during build (2026-09-23, defaults for the maintainer to confirm or override)

1. A file with no heading at all stays one rule with its 0.1.0 id and state; a heading-less file is
   never dropped. In a file with headings, text above the first heading is no rule, documented as a
   known miss in the `ruleprobe/rules.py` docstring and the README.
2. AD-12 gives a bound file's id as its path; 0.1.0 uses its `rule:` name, else its file name. This
   story keeps the 0.1.0 id (AC 5). The conflict is recorded here; the spine is amended separately.
3. The README's worked-example output and its "a rule file is one rule" paragraph are updated in this
   change to describe section rules.
4. The coverage block's 27-character rule column is left alone here, so section ids print cut; RP-S014
   edits that function and merges first, and the column is widened after a rebase onto it.

Amendment, 2026-09-23: after the rebase onto RP-S014, decision 4 is carried out. The coverage
block prints every rule id whole, widening the column to the longest id with the old 28-character
width as its floor, so section ids no longer print cut.

Decisions taken during review (2026-09-23, beyond the story; for the maintainer to confirm or
override):

5. The summary's findings header reads `findings: N (everything else still loaded)`, so it fits a
   skipped detector entry and a section-id collision alike.
6. A `rule:` key on a file that splits into section rules is a finding: its rules are named by path
   and heading.
7. Rule files are read as `utf-8-sig`, so a byte order mark does not hide the first heading.
8. Front matter that is empty or holds only YAML comments is an empty mapping, not "not a mapping".
9. Beyond fences, tables and blockquotes, these are not text: HTML comments (a `#` inside one is no
   heading), indented code blocks, thematic breaks, and a line of only images or only a link
   reference definition.
10. A heading with nothing left to slug, only punctuation or emoji, takes `section` as its base slug.
11. A headed file takes section ids even with one section, so an id does not change when a section is
    added below it (AD-12's stability).
12. A `detector:`, `detectors:` or `opt_out:` key with no value binds nothing, as in 0.1.0: the file
    takes the unbound path and the key is a finding. A headed file none of whose sections is a rule
    stays one unmeasured rule with its 0.1.0 id and the reason "no section is a rule".

### Do not implement

- Catalog binding (RP-S016); every split rule is unmeasured here.
- Per-section front matter or opt-out syntax; the corpus records none.

### Completion notes

- `read_rule_file(path, root=None)` now returns `(detectors, [RuleEntry], findings)`. A file whose
  front matter carries `detector:` or `opt_out:`, fails to parse, or is not a mapping keeps the 0.1.0
  path and one entry. Any other file is split at ATX headings of every level; a `#` line inside a
  fenced block is not a heading.
- A section is a rule when a line under its heading has a letter or digit outside a fenced block,
  an indented code block (after a blank line or a heading), an HTML comment, a table (with or
  without edge pipes) and a blockquote (lazy continuation stops at a list item). A thematic break,
  an image-only line and a link reference definition are not text, and a `#` line inside a comment,
  even one opened mid-line, is not a heading. A heading with nothing to slug takes `section`; a
  link's target and emphasis markers stay out of a slug. `_sections` and `_slug` are private.
- A bare `detector:`, `detectors:` or `opt_out:` key binds nothing and is a finding (decision 12);
  empty or comment-only front matter is an empty mapping; a byte order mark is dropped on read.
- The id is `<path relative to --rules>#<slug>`, carried in `RuleEntry.rule`. Ordinals count every
  heading, rule or not, so an id does not move when a section above changes whether it is a rule. A
  rule id that still repeats is a finding on its heading's line; both rules stay listed.
- A file with no heading keeps the 0.1.0 path: one unmeasured rule named by its `rule:` key or its
  file name (decision 1). In a headed file, text above the first heading is no rule.
- After rebasing onto RP-S014, the coverage block prints every rule id whole, the column widened to
  the longest id with the old 28-character width as its floor (decision 4); a README test checks the
  whole example block.
- Setext headings do not split. A `rule:` key on a split file is a finding: its rules are named by
  path and heading. The findings header now reads `findings: N (everything else still loaded)`, which
  fits both a skipped detector entry and a section-id collision.
- New tests sit in `tests/test_rule_sections.py` rather than `tests/test_rules.py`, which a parallel
  story may edit; `tests/test_rules.py` and `tests/test_schema_version.py` only take the new return
  shape and ids.

## Review findings

`bmad-build` review, three layers (blind hunter, edge-case hunter, verification gap), run on the
commit before the rebase onto story 3.3; each finding was checked against the rebased code:

- **Patched, medium:** a `___` break counted as rule text; HTML comments counted as text and a `#`
  line inside one split the file; the three single-rule error paths on a headed file had no test.
- **Patched, low:** a heading with nothing to slug gave `x.md#`; a byte order mark hid the first
  heading; empty front matter stopped the split; a `rule:` name on a split file vanished silently; the
  findings header claimed every finding skipped an entry; the README said coverage counts rule files.
- **Rejected, by design:** "renaming a section above can renumber a later one with the same slug":
  ordinals follow document order, as AD-12 says.
- **Deferred to story 3.5:** a section id carries its file's path, which holds `/` in a subdirectory,
  while a rule name holds no slash; the catalog story settles how such a rule binds.

`bmad-code-review`, four layers (blind hunter, edge-case hunter, verification gap, acceptance
auditor):

- **Patched, high:** the build review's fix made a bare `opt_out:` file dark where 0.1.0 read it as
  unmeasured, and a bare `detector:` compile a null entry; a key with no value binds nothing again,
  as in 0.1.0, with a finding on its line.
- **Patched, medium:** a headed file whose sections are all non-rules vanished from coverage; it stays
  one unmeasured rule with its 0.1.0 id and the reason "no section is a rule".
- **Patched, low:** a bullet after a quote, text after `-->`, a comment opened mid-line, indented code
  after a fence, image-only lines and link references are classed correctly; slugs drop link targets
  and emphasis; `_slug` and `_sections` are private; comment-only front matter reads as empty; tests
  cover CRLF, the fence branches, an undecodable file and the CLI count (AC 1).
- **Rejected, by design:** "a file with one heading loses its 0.1.0 id": headed files take section ids
  even with one section, so an id does not change when a section is added below it (AD-12).
- **Patched, low:** the changelog carries the change under `### Breaking`, added when the branch is
  rebased onto `main`.
