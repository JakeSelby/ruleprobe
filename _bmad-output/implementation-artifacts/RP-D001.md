# RP-D001 — decision(contract): the schema version's type and the value 0.2.0 writes

- **Primary parent:** [RP-E003](https://github.com/JakeSelby/ruleprobe/issues/22)

The issue carries the summary, discussion and acceptance evidence; this file carries the design.

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Context

FR-27 and FR-28 put a schema version on every detector entry, every row and every `report_data`
result. AD-9 fixes the key (`schema_version`) and that an absent key means 1, and names integer as the
PRD glossary's working type, but leaves the type and the value 0.2.0 writes open under PRD Q9. Every
later story writes rows and entries under this value, so it must be fixed before stories 1.4 and 1.5
write it. A stored row keeps the value for good.

Current behaviour (0.1.0): no entry or row carries a schema version. `ENTRY_KEYS` in
`ruleprobe/matchers.py` has no `schema_version`, and `ruleprobe/detectors/common.yaml` carries a
top-level `version: 1` that 0.1.0 ignores.

## Options

1. **Integer, 0.2.0 writes `2`.** The case for: absent already means 1 under AD-9, so the 0.1 schema is
   1 and the first versioned schema is the next integer; comparison against "the highest known" is a
   plain integer compare; it matches the top-level `version: 1` already in `common.yaml`. The case
   against: the number does not say which package release wrote it.
2. **Integer, 0.2.0 writes `1`.** The case for: the first explicit version is 1. The case against: an
   absent key also means 1, so a 0.1 row and a 0.2 row could not be told apart, and the 0.2 break
   changes counts (#19), so they are not the same schema.
3. **A string such as the package version (`"0.2.0"`).** The case for: self-describing. The case
   against: ordering needs parsing, a patch release would change the value without a schema change,
   and FR-31 says the schema does not change within a minor series.

## Decision

Decided 2026-09-23 by the maintainer: the schema version is an integer; 0.2.0 writes `2`; an absent
key means 1. Absent already means 1 under AD-9, so the 0.1 schema is 1, the first versioned schema is
the next integer, and comparison against the highest known is a plain integer compare.

## Consequences

- Stories 1.4 and 1.5 compare integers against one highest-known constant, `2` in 0.2.0.
- A 0.1 row or entry with no key reads as 1; a 0.2 row or entry reads as 2.
- `common.yaml`'s top-level `version: 1` stays valid as a default of 1 or is raised to 2 by story 1.4.
- AD-9 stands unamended, and states the integer and the value 2.
- The value lands in the contract test (story 1.8) and the versioning policy (story 1.9).
