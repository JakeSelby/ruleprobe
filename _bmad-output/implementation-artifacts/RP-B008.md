# RP-B008 — fix(readers): a Gemini write the user edited is not read as the agent's

## Reproduction

At `3028d3a`, a Gemini CLI session under a POSIX `.project_root` whose `gemini` record holds one
`write_file` call with these args:

- `content`: `"[default]\naws_secret_access_key = …\n"`, the version the user typed;
- `modified_by_user`: `true`;
- `ai_proposed_content`: `"[default]\n"`, what the model proposed.

`gemini.read` gives a `Write` tool use whose `content` is the user's text, and
`secrets/secret-in-write` hits it: the report counts a secret the user typed as one the agent
wrote. A `replace` the user edited gives an `Edit` whose `new_string` is the user's edited file
and whose `old_string` is the file as it stood. Found by the Epic 5 retrospective (action
item 23), which reproduced the `secret-in-write` hit.

## Root cause

`_call` in `ruleprobe/readers/gemini.py` maps `write_file` to `Write` and `replace` to `Edit` and
passes the recorded args through. When the user edits a proposal before accepting it, Gemini's
modify flow rewrites the args: the user's version replaces `content` (a write) or `new_string` (an
edit, whose `old_string` becomes the file's current content), `ai_proposed_content` keeps the
model's original `content` or `new_string`, and `modified_by_user` is set to `true`. The #54 spike
recorded this for `write_file` (RP-SP003, reader rules) but RP-S019's design carried no rule for
it, so the reader read the user's text as the agent's write: an over-count, against AD-4.

## Acceptance criteria

1. **Given** a `write_file` with `modified_by_user: true` and `ai_proposed_content`, **when** it
   is read, **then** it is a `Write` whose `content` is `ai_proposed_content`.
2. **Given** a `replace` with `modified_by_user: true` and `ai_proposed_content`, **when** it is
   read, **then** it is an `Edit` whose `new_string` is `ai_proposed_content` and which carries no
   `old_string`.
3. **Given** a `write_file` or `replace` with `modified_by_user: true` and no string
   `ai_proposed_content`, **when** it is read, **then** it keeps its native name, and no `Write`
   or `Edit` detector reads it.
4. **Given** a `write_file` or `replace` with no `modified_by_user`, **when** it is read, **then**
   its name and args are as before.
5. **Given** a write whose secret appears only in the user's version, **when** the detectors run,
   **then** `secrets/secret-in-write` does not hit; **given** the secret in the model's proposal,
   **then** it still hits.
6. **Given** the shipped corpus, **when** `ruleprobe corpus --no-config --floor 0.9` runs,
   **then** it passes.

## Design

### Approach

`_call` hands a `Write` or `Edit` whose args carry a truthy `modified_by_user` to `_proposal`.
With a string `ai_proposed_content` it returns the canonical name and the args with the proposal
in `content` (a write) or in `new_string` (an edit, with `old_string` dropped). Without one it
returns the native name and the args unchanged. The `tool_result` takes the same name. The rule
is stated in the module docstring and in the README's Gemini note.

### Decisions and alternatives

- 2026-09-24: an edited `replace` reads `ai_proposed_content` as its `new_string`. The spike
  cites the field for `write_file` only; Gemini CLI's public `edit.ts` declares the same field
  on the `replace` params and its modify flow sets it to the original `new_string` (read at
  `google-gemini/gemini-cli@87de0b6`, `packages/core/src/tools/edit.ts` L420–425 and L1303–1316).
  No code was copied.
- 2026-09-24: an edited `Edit` carries no `old_string`. The modify flow writes the file's
  current content there, not the model's `old_string`, which is not recorded. No detector reads
  `old_string` today; dropping it keeps a future one from reading file content as the agent's.
- 2026-09-24: with no proposal recorded the call stays native (`write_file`, `replace`), per
  AD-4: the agent's write is not known, so no detector measures it.
- 2026-09-24: `modified_by_user` is tested for truth, not for `true` exactly, so an unexpected
  truthy value leans to the under-count side.
- Rejected: dropping an edited call entirely. It ran, and a native tool use keeps it visible to
  anything counting tool calls by name.
- Rejected: reading the user's version and the proposal both. Only the proposal is the agent's.

### Must not change

Every call without `modified_by_user`: its name, its args and its relative-path resolution, and
every detector's hits on the shipped corpus.

## Regression test

`tests/test_reader_gemini_user_edit.py`. Against `3028d3a`'s `gemini.py` it gives
`Ran 7 tests`, `FAILED (failures=6)`; the unedited-write test is the one that passes on both. With
the fix all 7 pass.
