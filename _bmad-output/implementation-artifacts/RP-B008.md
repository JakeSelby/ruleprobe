# RP-B008 — fix(readers): a Gemini write the user edited is not read as the agent's

## Reproduction

At `3028d3a`, a Gemini CLI session under a POSIX `.project_root` whose `gemini` record holds one
`write_file` call with these args:

- `content`: `"[default]\naws_secret_access_key = …\n"`, the version the user typed;
- `modified_by_user`: `true`;
- `ai_proposed_content`: `"[default]\n"`, what the model proposed.

`gemini.read` gives a `Write` tool use whose `content` is the user's text, and
`secrets/secret-in-write` hits it: the report counts a secret the user typed as one the agent
wrote. A `replace` the user edited gives an `Edit` whose `new_string` is the user's edited file
and whose `old_string` is the file as it stood. Found by the Epic 5 retrospective (action
item 23), which reproduced the `secret-in-write` hit.

## Root cause

`_call` in `ruleprobe/readers/gemini.py` maps `write_file` to `Write` and `replace` to `Edit` and
passes the recorded args through. When the user edits a proposal before accepting it, Gemini's
modify flow rewrites the args: the user's version replaces `content` (a write) or `new_string` (an
edit, whose `old_string` becomes the file's current content), `ai_proposed_content` keeps the
model's original `content` or `new_string`, and `modified_by_user` is set to `true`. The #54 spike
recorded this for `write_file` (RP-SP003, reader rules) but RP-S019's design carried no rule for
it, so the reader read the user's text as the agent's write: an over-count, against AD-4.

## Acceptance criteria

1. **Given** a `write_file` or `replace` with a truthy `modified_by_user`, with or without
   `ai_proposed_content`, **when** it is read, **then** it keeps its native name and its input
   holds none of `content`, `new_string`, `old_string` or `ai_proposed_content`.
2. **Given** a `write_file` or `replace` with `ai_proposed_content` and no truthy
   `modified_by_user`, **when** it is read, **then** it is treated as edited, as in AC 1.
3. **Given** an edited call with a relative `file_path` under a POSIX root, **when** it is read,
   **then** `file_path` is resolved as for any write, and `modified_by_user` stays in its input.
4. **Given** a `write_file` or `replace` with neither field, **when** it is read, **then** its
   name and args are as before.
5. **Given** a write whose secret appears only in the user's version, **when** the detectors run,
   **then** `secrets/secret-in-write` does not hit.
6. **Given** the shipped corpus, **when** `ruleprobe corpus --no-config --floor 0.9` runs,
   **then** it passes.

## Design

### Approach

A call the user edited is not measured as a write. `_call` asks `_user_edited` whether a
`write_file` or `replace` carries a truthy `modified_by_user` or an `ai_proposed_content` key; if
so, the call keeps its native name and loses `content`, `new_string`, `old_string` and
`ai_proposed_content` from its input, so neither a `Write`/`Edit` detector nor a declarative `arg`
rule without a tool filter reads text that may be the user's. `file_path` is still resolved
against a POSIX root, and `modified_by_user` and the other keys stay. The `tool_result` takes the
native name. The rule is stated in the module docstring and in the README's Gemini note.

### Decisions and alternatives

- 2026-09-24, code review: supersedes the first two superseded entries below. A call the
  user edited stays native with its text args dropped, whether or not a proposal is recorded.
  Two doubts decide it. For `replace`, reading `ai_proposed_content` as the model's `new_string`
  rests on one reading of one pinned `edit.ts`, and a reviewer reads the modify flow
  differently. For both tools, when the user opens the editor twice before accepting,
  `ai_proposed_content` can hold the user's first edit, and nothing in the record tells the
  rounds apart. Under AD-4 the agent's write is then not known, so it is not measured.
- 2026-09-24, code review: `ai_proposed_content` present without the flag counts as edited, so
  a record that drops the flag still under-counts.
- 2026-09-24, code review: supersedes the third superseded entry below. The text args are dropped as well as
  the name kept native, since a declarative `arg` rule with no tool filter matches any
  `tool_use` input whatever its name.
- 2026-09-24, superseded: an edited `replace` reads `ai_proposed_content` as its
  `new_string`. The spike cites the field for `write_file` only; Gemini CLI's public `edit.ts` declares the same field
  on the `replace` params and its modify flow sets it to the original `new_string` (read at
  `google-gemini/gemini-cli@87de0b6`, `packages/core/src/tools/edit.ts` L420–425 and L1303–1316).
  No code was copied.
- 2026-09-24, superseded: an edited `Edit` carries no `old_string`. The modify flow writes the
  file's current content there, not the model's `old_string`, which is not recorded. No detector reads
  `old_string` today; dropping it keeps a future one from reading file content as the agent's.
- 2026-09-24, superseded: with no proposal recorded the call stays native (`write_file`,
  `replace`), per AD-4: the agent's write is not known, so no detector measures it.
- 2026-09-24: `modified_by_user` is tested for truth, not for `true` exactly, so an unexpected
  truthy value leans to the under-count side.
- Rejected: dropping an edited call entirely. It ran, and a native tool use keeps it visible to
  anything counting tool calls by name.
- Rejected, superseded: reading the user's version and the proposal both. Only the proposal is
  the agent's. Neither is now read.

### Must not change

Every call with neither `modified_by_user` nor `ai_proposed_content`: its name, its args and its
relative-path resolution, and every detector's hits on the shipped corpus.

## Review findings

Code review, round 1 (blind hunter, edge-case hunter):

- **Resolved by the design change, blocker:** an edited `replace` read from
  `ai_proposed_content` may read the file or the user's text as the agent's. It stays native.
- **Resolved by the design change, should-fix:** a repeated modify can put the user's first edit
  in `ai_proposed_content`. No edited call reads it.
- **Resolved by the design change:** an edited call's text args were kept on a native call,
  where a name-less `arg` rule reads them. They are dropped.
- **Resolved by the design change:** `ai_proposed_content` without the flag was read as unedited.
  It counts as edited.
- **Patched, should-fix:** tests added for relative-path resolution on an edited call, a truthy
  non-`True` flag and the native `tool_result` name. The replace-shape and proposal-secret
  findings no longer apply: no proposal is read.
- **Patched, note:** the README no longer says no detector reads a native edited call; it names
  the dropped args.
- **Patched, note:** the B004/B006 swap in `issue-map.json` is reverted to `origin/main`'s order.
